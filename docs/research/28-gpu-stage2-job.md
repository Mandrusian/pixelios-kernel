# 28 - G2 stage 2: address space 0 and the first job (`--gpu-s2mpu`, `--gpu-job`)

Status 2026-10-23: design, code, host tests and audits are built; **nothing has run on hardware**. Tags: *observed* (hardware, run), *read from source* (file:line), *guess*.
Goal: the GPU writes a magic 64-bit value to a RAM word through its own MMU. That proves AS0 programming, the page-table format, the job manager start, and whether the G3D S2MPU lets
GPU DMA reach shim RAM (open unknown #3 of doc 17 section 5). Preconditions that are *observed*: tiler + L2 + 20 shader cores power up with the S2MPG11 BUCK2S rail on (run `railon2`,
`up=ok down=ok`, `SHADER_READY=0x779FFF`, doc 27).

## 1. The flags
- `--gpu-s2mpu` (implies `--gpu-probe`): **read-only** dump of the four G3D S2MPU blocks (section 5). May be run and committed on its own, first. Audit: same read-only policy as `gpuprobe.o` (stack-only stores, no `try_write32` reference).
- `--gpu-job` (implies `--gpu-probe --gpu-rails --gpu-rail-on --gpu-power --gpu-s2mpu`; not with `--gpu-power=stack`): after the rail is on and the shaders are up, `gpu_power_cycle()` calls `gpu_job_run()` once (hook in `gpupower.c`, only `if (up[0] == 'o')`), then the normal OFF sequence and the rail restore run as before. Audited objects: `gpujob.o` (writer), `gpupower_job.o` (= `gpupower.o` plus the one call).

## 4. The job (Valhall, arch 9) and the job slot
Mesa `v9.xml` (commit above): `Job Header` align 128 (`:1444-1459`): word 0 Exception Status, word 1 First Incomplete Task, words 2-3 Fault Pointer, **word 4: Type bits 7:1**, Barrier bit 8, Suppress Prefetch 11,
Relax Dependency 1/2 bits 14/15, Index bits 31:16; word 5 Dependency 1 / 2; words 6-7 Next. The comment "All jobs are 64-bit" replaces the `Is 64b` bit 0 of `v6.xml:1257` (bit 0 stays 0 on Valhall). `Job Type`: Write value = 2 (`:40`).
`Write Value Job Payload` (`:1487-1491`) at offset 32: Address (64) at +0, **Type (32) at +8**, **Immediate Value (64) at +16**; `Write Value Type` (`:1477-1485`): Immediate 64 = 7. Aggregate "Write Value Job" = Header @0 + Payload @32, align 128.
| Data page offset | Contents |
|---|---|
| +0x10 | header word 4 = `(1 << 16) \| (2 << 1)` = **0x10004**: Index 1 (Mesa numbers jobs from 1: `pan_jc_add_job` does `index = ++jc->job_index; header.index = index`, `src/panfrost/lib/pan_jc.h:159-165` at the pinned commit; the dependency scoreboard is index-based), Type 2; all other header words 0 (no dependencies, Next 0) |
| +0x20 | payload Address = target VA `0x1100` |
| +0x28 | payload Type = 7 (Immediate 64) |
| +0x30 | Immediate Value = `0x504958454C494F53` ("PIXELIOS") |
| +0x100 | target word, pre-set to `0xA5A5A5A5A5A5A5A5` so "unchanged" differs from "zero written" |
**Which slot (review M1).** Mesa/panfrost sends only fragment jobs to JS0; everything else, including the chains that hold WRITE_VALUE jobs, goes to JS1: Linux `panfrost_job_get_slot()` returns 0 for fragment, else 1 (`drivers/gpu/drm/panfrost/panfrost_job.c:111-131`, local copy `refs/gpu-stage2/linux_panfrost_job.c`, linux master file commit c9126bf8fcb5). Whether JS0 can run a WRITE_VALUE job is a hardware capability: `JS_PRESENT` (0x1C) bit 0 and `JS0_FEATURES` (0xC0) bit 2 `JS_FEATURE_SET_VALUE_JOB` (`regmap_jm_macros.h:230`; offsets `regmap_jm_enums.h:41,70`). The precheck therefore READS them and refuses with ZERO writes unless both hold; `JS_PRESENT`, `JS0..2_FEATURES` are printed either way. If JS0 turns out not to take WRITE_VALUE, the next step is JS1 (the slot panfrost uses): not built, it would need a second allowlist block (`JS1` = +0x80), decided after seeing the printed features.
Job slot 0 (`JOB_CONTROL` 0x1000, `JS0` at +0x800; offsets `regmap_jm_enums.h:112-140`): kbase `kbase_job_hw_submit` (`jm_hw.c:119-262`) waits `JS0_COMMAND_NEXT == 0` (`:101-117`), then writes `HEAD_NEXT` (64-bit, 0x1840), `AFFINITY_NEXT` (0x1850; Bifrost+ = `shader_present`, `jm_hw.c:60-96`), `CONFIG_NEXT` (0x1858), `COMMAND_NEXT` = `JS_COMMAND_START` 1 (0x1860).
`CONFIG_NEXT` = `as_nr (0)` \| `START_FLUSH_CLEAN_INVALIDATE` (3 << 8) \| `END_FLUSH_CLEAN_INVALIDATE` (3 << 12) \| `JOB_CHAIN_FLAG` (1 << 11, first job of the slot) \| `THREAD_PRI(8)` (8 << 16) = **0x83B00** (`jm_hw.c:151-203`; defines `regmap_jm_macros.h:149-171`). We take the branch kbase uses when `CLEAN_ONLY_SAFE` is absent (`jm_hw.c:191-195`; whether tBEx has it is **not cited**), and not `FLUSH_REDUCTION`/`FLUSH_ID_NEXT` (feature support not cited).
kbase's current code does not set `JS_CONFIG_START_MMU` (bit 10) although its comment says "start MMU" (`jm_hw.c:147-152`): we follow the code. Independent confirmation (Opus review I1): kbase's own dummy-job workaround starts jobs with `CONFIG_NEXT = DISABLE_DESCRIPTOR_WR_BK | as` (`kbase-bluejay/mali_kbase_dummy_job_wa.c:91-92`), no START_MMU, no flush. It is NOT the first suspect for a timeout; a JS0 without the capability is (see above).
Completion: `JOB_IRQ_RAWSTAT` 0x1000 bit 0 = slot 0 done, bit 16 = slot 0 failed (`jm_hw.c:300-303`); `JOB_IRQ_CLEAR` 0x1004 `done & (1 << i | 1 << (i + 16))` (`:374-375`). RAWSTAT is readable with the interrupt masked (no IRQ is unmasked). On a timeout kbase hard-stops with `JS_COMMAND_HARD_STOP_1` (7) when the atom carries `JOB_CHAIN_FLAG` (`jm_hw.c:532-537`, write to `JS0_COMMAND` 0x1820, `:540`); we do that once after 100 ms and wait 100 ms more.
`JS0_STATUS` 0x1824, `JS0_HEAD` 0x1800 and `GPU_FAULTSTATUS` 0x3C are printed.

## 5. Memory and caches
- **Scratch**: `shim.c` reserves `gpujob_pages[6 * 4096]` (only with `--gpu-job`); the base is aligned up to 4 KiB at run time (the image load address is not known at link time). 5 pages are used: L0, L1, L2, L3, data. It lies inside the shim image's own RAM: it is `.bss`, inside `image_size = _end` of the boot-image header (`start.S:8`), so a loader that honours the header does not place the DTB or ramdisk there (*read from source*); that ABL actually honours it is a *guess*. XNU is not loaded in a probe image (`bluejay_probe` runs before `loader_boot`, and `--boot-xnu` is a different path). It is the *only* RAM the writer may touch: `w32_allowed` accepts aligned words inside `[base, base + 5 * 4096)`.
  This isolates the S2MPU question to one granule: the dump prints the L1 entry of the granule containing the scratch (`gb_index = PA >> 30`). A later variant can target the XNU bank (granule 0x22 and up) to answer the "can GPU DMA reach XNU RAM" half; not built (needs the answer here first).
- **CPU side**: the shim runs MMU-off, i.e. every CPU data access is Device-nGnRnE and bypasses the caches; the risk is stale dirty lines of the *previous* owner of those physical lines. `gpu_job_cache_flush()` (`DC CIVAC` per 64-byte line then `DSB SY; ISB`; MMU off => VA == PA) runs over all 5 pages before the tables are built, after they are built (so nothing is written back over them), and over the data page before the result is read. *Guess*: this is enough; the cache line size of 64 bytes is the Cortex-A55/A76 value, not read from CTR_EL0.
- **GPU side**: MEMATTR index 5 = non-cacheable inner/outer, so the job and the target word are not allocated in the GPU L2; `END_FLUSH_CLEAN_INVALIDATE` cleans what was cached. The walker reads the tables with `PTW_MEMATTR` WRITE_BACK as kbase does; the L2 is empty of those lines, so it fetches from DRAM, where the CPU stores landed. `COHERENCY_ENABLE` reads 0 (*observed*, run `g2power`: `PRE_COHERENCY_ENABLE=0`); in upstream kbase `COHERENCY_ACE_LITE` = 0 and `COHERENCY_NONE` = 31 (*from memory, not in the local copies*), so 0 may mean ACE-Lite is selected. Harmless here: every leaf is non-shareable and non-cacheable and the walker has `PTW_SH` = 0. In this boot the GPU never saw kbase's soft reset or its quirk writes (JM/SHADER/TILER/L2_MMU_CONFIG); if the result is `failed`, that is a possible cause (*guess*).

## 6. S2MPU (read-only; never written)
Four instances `s2mpu_g3d0..3` at `0x20080000 / 0x20090000 / 0x200A0000 / 0x200B0000`, size 0x10000, power domain id `0x1C410204` (= `pd_g3d`) (`gs101-b0.dts:58-69`, `gs101-s2mpu.dtsi:139-161`).
Registers (`s2mpu-regs.h`): `CTRL0` 0x00 (ENABLE bit 0, INTERRUPT_ENABLE bit 1, FAULT_RESP_TYPE bit 2), `CTRL1` 0x04, `CFG` 0x10, `MPC_CTRL` 0x40, `PAGE_AWARE_DECODING_0/1` 0x44/0x48, `FAULT_STATUS` 0x2000, `FAULT_PA_LOW(n)` 0x2004 + n * 0x20, `FAULT_INFO(n)` 0x2010 + n * 0x20, `L1ENTRY_L2TABLE_ADDR(n, m)` 0x4000 + n * 0x200 + m * 8, `L1ENTRY_ATTR(n, m)` 0x4004 + n * 0x200 + m * 8 with n = VID (0 or 1, `s2mpu-lib.c:227`), m = gigabyte index (64 granules, `s2mpu-lib.h` `WHI_MAX_GB_GRANULES`); attr bits L2TABLE_EN bit 0, RD bit 1, WR bit 2, GRANULE bits 5:4.
Why it matters: Linux re-programs the S2MPU when the GPU powers up (`pm_runtime_get_sync(kbdev->s2mpu_dev)`, `pixel_gpu_power.c:265-267`; the S2MPU driver restores its table, `s2mpu_lib_restore`, `s2mpu-lib.c:~750-800`), so its state after ABL (the `g2` runs never touched it) is unknown: it may still block all of DRAM, or ABL may have opened it. Whether `CONFIG_MALI_PM_RUNTIME_S2MPU_CONTROL` is set in the Pixel build is **not cited** (the code exists under that config, `pixel_gpu.c:200`).
Output (`--gpu-s2mpu`, and at the start of every `--gpu-job` run): `GPU S2MPU probe_pa=.. gb_index=..`; per instance `CTRL0, CTRL1, CFG, MPC_CTRL, PAGE_AWARE0/1, FAULT_STATUS`; per VID `FAULT_INFO`, `FAULT_PA_LOW`, `vidN rdwr=<64-bit mask of granules open RD+WR> l2=<mask of granules with an L2 table> nonzero= bad=`, and the exact `L1ATTR`/`L1L2ADDR` of the scratch's granule. `--gpu-s2mpu` passes the address of the dump function itself (the shim image) as `probe_pa`.
Reading is guarded (`try_read32`); a hang of the S2MPU block cannot be caught: the read happens only if `PMU_G3D_STAT` says `pd_g3d` is on. **Risk (*guess*)**: the S2MPU may not be readable from EL1 on this boot (secure/hypervisor-owned); a fault is printed as `unreadable`.

## 8. Sequence and outcomes
1. Read-only: `GPU JOB cfg ...`, the S2MPU dump, `JS_PRESENT`/`JS0..2_FEATURES`, `precheck` (refuses with ZERO writes: `scratch-bad`, `no-timer`, `js0-absent`, `js0-no-set-value`, `shaders-not-ready` (`SHADER_READY` != 0x779FFF), `job-irq-pending`, `mmu-irq-pending`, `as0-active`, `js0-busy`, `gpu-fault`).
2. Cache flush; zero the 5 pages; write the 4 table entries, the job, the target pattern; flush again.
3. AS0 write set + UPDATE + wait (`GPU JOB AS0_STATUS`); a failure here stops before any JS0 write.
4. JS0 submit (6 writes); wait up to 100 ms for a job event (RAWSTAT bit 0/16) or any MMU fault; once, `HARD_STOP_1` and 100 ms more.
5. Report (read-only): `JOB_IRQ_RAWSTAT`, `MMU_IRQ_RAWSTAT`, `JS0_STATUS`, `JS0_COMMAND_NEXT` (a START still pending is not touched by HARD_STOP; kbase would write NOP), `JS0_HEAD_LO`, `AS0_FAULTSTATUS`, `AS0_FAULTADDR_LO`, `GPU_FAULTSTATUS`, then `GPU JOB target=<64-bit> header_exc=<word 0 of the descriptor, written back by the GPU>`.
6. ALWAYS, in kbase's kill order: hard-stop a job that is still ACTIVE (`JS0_STATUS` == 0x08, `BASE_JD_EVENT_ACTIVE`, `mali_base_jm_kernel.h:729`; at most one hard stop in total, e.g. for a job stalled on an MMU fault), AS0 -> UNMAPPED, re-read `JOB/MMU_IRQ_RAWSTAT`, clear the slot-0 raw bits that are set; then `GPU JOB SUMMARY submit=<ok|no> wait=<done|failed|mmu-fault|timeout|n/a> hardstop=<yes|no> target=<MAGIC|unchanged|other> as0_off=<ok|FAILED>`. The function returns 0 only for `target=MAGIC`. The power-off sequence and the rail restore follow as before.
Reading the result: `target=MAGIC` = AS0, page tables, job start and S2MPU all work. `unchanged` with `wait=done` = the S2MPU (or a cache) dropped the write; `mmu-fault` = a table or attribute is wrong (`AS0_FAULTSTATUS`); `timeout` = the job never ran (see the `START_MMU` note); a S2MPU block may also show as `failed` with a `FAULT_STATUS` change in the S2MPU lines of the NEXT run.

## 9. Open unknowns / not cited (nothing here was guessed into code silently)
1. `JS_CONFIG_START_MMU` is not set (kbase's code, not its comment; confirmed by the dummy-job workaround, section 4). 2. `CLEAN_ONLY_SAFE` / `FLUSH_REDUCTION` support of tBEx not cited: we use the conservative CLEAN_INVALIDATE flushes and no flush id. 3. `system_coherency` of the Pixel and so `PTW_SH`: unknown, left non-shared. 4. S2MPU state after ABL, readability from EL1, and the config switch that makes Linux manage it. 5. Whether GPU DMA to the image's RAM behaves like DMA to the XNU bank (different granule, maybe different S2MPU entries). 6. The cache line size is assumed 64 bytes. 7. Behaviour of a hung job when the OFF sequence runs (no soft reset in the allowlist; `SHADER_PWRTRANS` may stick; reported by the OFF dump). 8. A real WRITE_VALUE job has only been run by Mesa/kbase on other GPUs (G52/G57/G78 per Mesa's tests, *guess*); the exact Valhall header bits other than Type are taken from `v9.xml` only.
These need the hardware run, and the Opus review of the writer before it.

## 10. Observed: G3D S2MPU state after ABL (run s2mpu1, 2026-10-23, `logs/probe/20261023T011845Z-s2mpu1_`, `--gpu-s2mpu`, read-only)
*Observed on hardware.* All four blocks (0x20080000/90000/A0000/B0000) are readable from EL1 and identical: `CTRL0=0` (ENABLE bit 0 = 0, INTERRUPT_ENABLE 0, per section 5 register layout), `CTRL1=3`, `CFG=0`, `MPC_CTRL=0`, `PAGE_AWARE0/1=00F200F1/00F400F3`, `FAULT_STATUS=0`, both VIDs: rdwr mask and L2-table mask `0`, no faults recorded. So the S2MPU is **disabled** (not programmed) after ABL. *Read from source (a comment), not observed:* a disabled S2MPU does not block: the Linux driver turns it on "to make sure that the S2MPU is enabled and hence blocking traffic" (`s2mpu-lib.c:168`), i.e. ENABLE = 0 blocks nothing, so GPU DMA to shim RAM should not be blocked; this is exactly what `--gpu-job` tests. (The run printed `RESULT: HANG` only because my `--expect` regex named a summary line the probe does not print; the dump was complete and the phone came back.)

## 11. RESULT: first GPU job executed (run job1, 2026-10-23, `logs/probe/20261023T013806Z-job1_`)
*Observed on hardware* (`tools/probe-run --build-args "--pstore-fast --gpu-probe --gpu-rails --gpu-rail-on --gpu-power --gpu-job"`, commit with the Opus review fixes M1-M3, L1-L3; `fastboot boot` only). `GPU JOB SUMMARY submit=ok wait=done hardstop=no target=MAGIC as0_off=ok`: the Mali-G78 walked our 4-level 4 KB page tables from AS0, executed a Valhall WRITE_VALUE job on JS0 and wrote `0x504958454C494F53` ("PIXELIOS") to the scratch word at PA 0x08001B100-ish (target_va=0x1100); job header exception status 1 (DONE), JOB_IRQ_RAWSTAT=1 (slot 0 done, no failure bit 16), MMU_IRQ_RAWSTAT 0, AS0_FAULTSTATUS 0, GPU_FAULTSTATUS 0.
